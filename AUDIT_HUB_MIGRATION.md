# Audit & Migration Plan — Portal off ClickUp/Make onto Hub D1 (`s27-crm-db`)

> Scope: re-point the LIVE customer portal `portaal.studio27.be` (this repo `/home/user/klantenportaal`) so it reads/writes the new internal CRM Cloudflare D1 database `s27-crm-db` (`0c50db87-9a69-4cdc-9f43-4c1dc92dd801`) instead of ClickUp-via-Make.
> Synthesised from 8 parallel auditor findings. Where finders disagree or left an open question, it is flagged inline as **[OPEN]** / **[DISAGREEMENT]**.

---

## 1. Executive summary

**What this migration is.** Today every backend call the portal makes goes `frontend → Cloudflare Worker gateway → Make.com webhook → ClickUp`. The goal is to make those same calls read/write the Cloudflare D1 database `s27-crm-db` directly, so the portal stops depending on ClickUp+Make for customer-facing data.

**Current state (verified).**
- The LIVE frontend is `dashboard.js` (~5600 lines). It funnels **all** traffic through `api()` (line 283) → `apiV2()` (line 305), which POSTs to `GATEWAY_BASE = https://s27-portal-gateway.studio27marketing.workers.dev` (line 60) with an `Authorization: Bearer <Firebase ID-token>` header.
- That URL resolves to the thin 333-line proxy in this repo, `gateway/worker.js`. It verifies the Firebase token, reads `bedrijf_id` from a **custom claim** (never the body), overrides `body.bedrijf_id/uid/email/session_token`, and forwards to a Make webhook from `MAKE_ENDPOINTS`. It returns the upstream body verbatim as `{ok,status,data}`.
- A separate **deployed** worker `s27-portal-gateway-v2` (source NOT in repo; full dump on disk) contains both the `MAKE_ENDPOINTS` proxy AND CRM/D1 logic. **Critical correction (Finding 2):** the v2 portal-facing READ/WRITE handlers do **not** read D1 — they call ClickUp directly via a `cu` helper. The only ClickUp→D1 writes are the manual ops-gated sync endpoints `crm/sync` (`crmSyncAll`) and `crm/syncoff`. **The live portal does NOT point at v2; it runs 100% on Make→ClickUp.**
- D1 is therefore a **one-directional ClickUp→D1 mirror** of `companies` (491), `contacts` (261), `meetings` (416/417), `offertes` (~402). `tasks` (255) are stub rows generated by the offerte-intake processor. `task_comments`, `chat_messages`, `files`, `social_posts`, `invoices`, `invoice_lines`, `offerte_lines` are **empty (0 rows)**.

**The single most important finding (identity + sync direction).** Two facts dominate the whole migration:

1. **Identity mapping is clean.** The Firebase claim `bedrijf_id` is a ClickUp task-id, and for all 491 D1 companies `companies.id == companies.clickup_id == the claim` (verified 491/491, all 9-char ClickUp ids, 0 uuids). So **no id translation is needed** — `WHERE company_id = <claim>` works directly. **BUT** the two documented test companies `86c9yv1wy` and `86ca23kjx` return **zero rows** in D1 (every finder confirmed this independently), so parity testing must use a real synced company id or those two must be re-synced first.
2. **The sync is one-directional with a per-field write-guard.** `crmSyncAll` runs ClickUp→D1 via `cdbUpsertGuarded` (dump line 11023), which `ON CONFLICT(id) DO UPDATE` overwrites every column **except** keys recorded in that row's `portal_overrides` JSON (loaded by `loadPortalOverrides`, dump line 11007). 56/491 companies already carry `portal_overrides`, proving the mechanism is live. **Consequence:** any portal write to D1 that does NOT stamp `portal_overrides[col]=Date.now()` is silently clobbered on the next sync. This is the #1 write-safety rule and the central architectural constraint of the entire project.

**Headline conclusion.** Identity is solved; the blocker is data + write-safety. `companies / contacts / meetings / offertes` are well-populated and can be read from D1 first. `tasks / chat / feedback / deliverables / files / social / invoices` have effectively no D1 data and must stay on ClickUp until a sync backfills them or the hub becomes their authoritative store. Cut over read-only metadata first behind a per-endpoint flag with byte-for-byte response parity, then writes (via `portal_overrides`), then chat/files last.

## 2. Current architecture

### Live data flow
```
dashboard.js (api()/apiV2(), line 283/305)
  → POST GATEWAY_BASE/<endpointKey>  (Authorization: Bearer <Firebase ID-token>)
     GATEWAY_BASE = https://s27-portal-gateway.studio27marketing.workers.dev   (dashboard.js line 60)
  → gateway/worker.js (repo, 333 lines)
        verifyFirebaseToken (lines 98-128)  → claims.bedrijf_id (custom claim = ClickUp task-id)
        overrides body.bedrijf_id/uid/email/session_token (line ~306)   ← body bedrijf_id IGNORED
        forwards to MAKE_ENDPOINTS[path] with header X-Gateway-Secret
  → Make.com webhook
  → ClickUp (space 90159547188: Bedrijven 901520180288, Contactpersonen 901520180286,
             8 discipline lists, Offertes, Meetings, Portaal-inbox 901520180314)
  ← response body returned verbatim as {ok, status, data}
```
The frontend only branches on HTTP `401` (→ `handleSessionExpired`) and `403 error==='no_company_link'` (→ `tryProvision` JIT re-link + retry once, `apiV2` lines 322-337). It otherwise consumes `data.*` by **exact key**, with no schema validation — any key/casing/status-string drift breaks a tab silently.

**Two security notes that the migration must preserve:**
- `bedrijf_id`/`session_token` are still in **every** frontend payload but are **ignored** server-side (legacy artifacts for the `?auth=v1` fallback). The gateway derives `bedrijf_id` from the verified Firebase claim. A D1 handler must do the same and treat any body `bedrijf_id` as untrusted.
- The deployed `s27-portal-gateway-v2` enforces `scopeCheckTask(task, bedrijfId)` (dump line 1361) with `SCOPE_FAIL_CLOSED={read:true,write:true}` — a task with no Bedrijf relation fails closed. The D1 reimplementation must reproduce this as a SQL `WHERE company_id = <claim>` guard on every query.

### Gateway endpoint keys (paths the frontend POSTs to `/<key>`)
`dashboard, projectDetail, projectDetailV2, calendar, uploadProject, uploadAlg, bedrijfContent, bedrijfVoorkeuren, bedrijfUpload, bedrijfContact, meetingsList, meetingAvailability, chatPost, chatList, chatAttachment, directMessage, feedbackV2, newProjectIntake, aiStatusBot, pandadocPricelist, shootAvailability, huisstijlList, huisstijlUpload, huisstijlDelete, driveEnsure, facturatieSave, projectFacturatieSave, performance, bedrijfBeheer, beschikbaarheid, inplannen, provision (admin), perfreport (GET iframe).`

Plus three **v4-only** touchpoints (not in live `dashboard.js`): `bedrijfBeheer action=get_offertes`, and two **direct Make webhooks that bypass the gateway/Firebase entirely** — `METRICOOL_DIRECT` and `ADS_DIRECT` (scoped only by a form-posted `bedrijf_id`). `provision` and `shootAvailability` are also raw fetches (form-encoded) that do not go through the gateway's JSON path.

## 4. The hub data model

### Identity & scoping (the keystone)
- **`companies.id` == `companies.clickup_id` == Firebase claim `bedrijf_id`** (a ClickUp task-id). Verified 491/491, all 9-char, 0 uuids. So the gateway scopes with `WHERE id = ?1` / `WHERE company_id = ?1` binding the claim directly. **No translation layer needed.**
  - **Resilience hedge:** the schema documents `companies.id` as "ClickUp task-id OR uuid", so if the hub later reissues uuids the join breaks. Recommend `WHERE id = ?1 OR clickup_id = ?1` as a fallback, and/or pin the ClickUp id in the claim permanently.
- `contacts.id` are also ClickUp task-ids; link to company via `contacts.bedrijf_id`. **Linkage is incomplete:** 206/261 have a `bedrijf_id`, only **202** valid (4 dangling, 55 unlinked); 180 distinct companies have a contact.
- `tasks.company_id`, `projects.company_id`, `offertes.bedrijf_id`, `meetings.bedrijf_id` are the per-entity scope columns — the D1 analogue of the ClickUp "Bedrijf" relation. `entity_links(source_type='task',target_type='company',relation='for')` (192 rows) is a secondary source.
- **`hoofd_contact` holds a NAME string, not a contact-id**, in current synced data. Do not join `companies.hoofd_contact → contacts.id`; derive the primary contact via `contacts.bedrijf_id`.

### How the claim resolves to a row
`verifyFirebaseToken` → `claims.bedrijf_id` (ClickUp task-id) → `SELECT … FROM companies WHERE id = ?1`. Because `id == clickup_id == claim`, this is a direct hit for synced companies. The only failure mode is an **unsynced** company (e.g. the two test ids) — the row simply does not exist, and a D1 read returns empty where the ClickUp path would still resolve.

`companies.kbo → btw/ondernemingsnummer` · `fact_email → facturatie_email` · `fact_opm → facturatie_opmerkingen` · `mw → aantal_medewerkers` · `naam → bedrijfsnaam` · `tasks.branch → discipline` · `tasks.brief → beschrijving` · `tasks.est_min → time_estimate` · `tasks.fb_status → feedback_status` · `tasks.fb_link → feedback_link` · `meetings.id → meeting_id` · `meetings.verval → vervaldatum` · `offertes.titel → naam` · `offertes.panda_link → link` · `offertes.verval → vervaldatum` · `contacts.notif → voorkeur`.

## 5. Chat migration

**Today (no real chat store).** All client↔team messaging is ClickUp **task-comments**. The v2 worker implements `chatList` (dump 2156), `chatPost` (2816), `chatAttachment` (2839), `directMessage` (2997), `feedbackV2` (3351), and a company-level `commsChat*` (2943-2994) directly against ClickUp — not D1. A message is "from client" purely by a text prefix: `chatPost` prepends `"💬 [Klant: {klant_naam}]\n\n"` and `chatList` sets `is_klant` by detecting that prefix; team replies are plain comments by the API bot. Read receipts live in Workers KV (`chatread:{bedrijfId}:{taskId}:klant`). `directMessage` creates a ClickUp task in Portaal-inbox `901520180314`. `feedbackV2` creates a "Feedback ronde N" subtask + comment and flips the parent to `done` when all approved. The portal polls `chatList` every 15s (`pollChatTick`, dashboard.js 4372).

**Target D1 model.**

| Concern | D1 target |
|---|---|
| One conversation per company ("one room") | `chat_rooms` row with deterministic id `'co_'||companies.id`, `type='group'`, `members` json = contact-ids + team `tm_*` ids. Replaces `resolveCommsTask`. Leave the existing `id='team'` staff room untouched. |
| Per-project chat thread | `chat_messages(room_id='co_'||companyId, task_ref=taskId, from_member, text, files, ts)`. `chatList(task_id)` becomes a `WHERE room_id=… AND task_ref=…` query. |
| Per-deliverable feedback thread | `task_comments(task_id, who, member_id, text, internal, created_at)` with `internal=0` for the klant-visible summary, so the team app + reporting can read it. |
| Send a client message | INSERT `chat_messages` (+ upsert `chat_reads.last_read_ts`). **`from_member` set server-side from the claim** — never the body. Drop the `'💬 [Klant:]'` prefix. |
| Attachments | `files(entity_type='message', entity_id=<message id>, r2_key, naam, content_type, company_id, task_id, visibility)` in R2 bucket `s27-portal-files`; `chat_messages.files` json references them. Serve via a scoped `/media/<r2_key>` route. |
| Unread badge / read receipt | `chat_reads(room_id, member_id, last_read_ts)` compared against `chat_messages.ts`. Replaces the KV receipt; yields the `{client_read_at,last_team_ts,read_by_client}` shape the frontend tolerates. |
| `is_klant` derivation | `from_member NOT IN team_members` ⇒ klant. `auteur` ← `team_members.naam` OR `contacts.voornaam||' '||achternaam` OR company name. Removes the fragile prefix heuristic. |
| `directMessage` | `notifications(member_id=<recipient tm_*>, kind='portal_dm', title, body, entity_type='company', entity_id=companyId, channels)`. Twilio WA on 'terugbel' stays a side-effect recorded in `channels`. |

**Client identity.** Comes from the `contacts` row whose `contacts.bedrijf_id = company.id`. Where no contact resolves (55 unlinked contacts; some portal users have none), **fall back to `from_member = lowercased email`**. `contacts.id` is a ClickUp task-id, so a fresh D1-native contact would not exist in ClickUp — keep contact creation + portal-access grant on ClickUp for now.

**Room scoping (security).** `room_id = 'co_'||<company_id-from-claim>`, derived entirely server-side. Ignore any `room_id`/`from_member`/`klant_naam` in the body. Every read adds `WHERE room_id='co_'||claimCompanyId` and verifies the contact belongs to that company. Keep fail-closed `scopeCheckTask` semantics (→ 403 `scope_mismatch`).

**Migration realities (all finders agree):**
- `chat_rooms` has exactly **1 row** (`id='team'`, 13 staff `tm_*`); `chat_messages`=0; `task_comments`=0; `files`=0. The entire client-room concept and client-as-`from_member` identity is **greenfield**.
- **History loss on cutover:** existing conversations live only in ClickUp comments. Either backfill (extend `crm/sync` to copy ClickUp comments into `task_comments`/`chat_messages`) before flipping the read path, or dual-read (D1 + ClickUp) during a transition window. Validate by comparing comment counts per task.
- **[OPEN] task_ref anchoring:** per-project threads (`task_ref=task id`) vs one company room (`commsChat`) are two different ClickUp anchors today. D1 must reconcile which model the portal uses.
- No realtime: keep 15s polling initially; add indexes `chat_messages(room_id, ts)` and `chat_messages(room_id, task_ref, ts)`. Consider a Durable Object/WebSocket later (not required for parity).

### What stays a live external call (keyed off the D1 IDs above)
- **Performance report (`/perfreport`)** — the entire dataset (`periode_meta_campaign`, `dag_meta_campaign`, TikTok/Snapchat/Google insight rows, `client_name/start_date/end_date`) lives only in the Make ads-cache datastore `ADS_RAPPORTEN`, keyed by `bedrijf_id`. **There is no `ads_reports`/`insights` table in D1.** Move only the key resolution (resolve `meta_ads/ga4/gads` from `companies` instead of ClickUp); keep the report in cache (KV/R2/Make) and keep the `client_name||start_date||periode_meta_campaign` presence shape.
- **Metricool content calendar (v4)** — `/scheduler/posts` stays a live Metricool fetch keyed by `companies.metricool`.
- **Meta ads campaigns (v4)** — live Meta Graph insights keyed by `companies.meta_ads`.
- **Socials/ads/SEO "doorlopend" tabs** in the LIVE `dashboard.js` are just project-card lists filtered from the `dashboard` feed by `discipline==='social'|'ads'|'seo'` — they show no Metricool/ads metrics. Those come from the `dashboard`/`tasks` migration, not from social tables.

### Important caveats
- `social_posts` is **empty (0 rows)** — the content calendar **cannot** be served from D1 until a Metricool→D1 sync backfills it (and per-network status/url detail is modeled; `social_posts` only has a single `status` + `platform[]`). Keep it a live Metricool fetch.
- `integrations` rows are **global** (`org=''`, `config '{}'`) — they carry no per-company keys and cannot scope a client. Per-company scoping comes only from `companies.*`.
- **ID-format normalization needed:** `gads` appears both dashed (`864-455-0588`) and raw (`2100979060`); `gsc` appears as full URL (`https://farmamatch.be/`) and as `sc-domain:…`. Normalize (strip dashes; coerce `gsc` to the API's `siteUrl` form) before calling the platform APIs.
- **Two-phase pattern:** read cheap connection id from D1, then live-fetch with try/catch returning `{ok:true,linked:true,…,posts:[]}` on failure (mirrors `metricool()` dump 4214). Short timeouts + cache last-good. Stale D1 IDs (edited in ClickUp, not yet synced) silently break stats → sync `companies.metricool/meta_ads/ga4/gads/gsc` frequently or make the hub the source of truth for these IDs.
- **Security:** the v4 `METRICOOL_DIRECT`/`ADS_DIRECT` webhooks bypass the gateway and trust a form-posted `bedrijf_id` — route them through the authenticated gateway and scope off the claim.

## 9. Recommended architecture decision

**Decision: Option A — add a D1 binding + per-endpoint D1 handlers to the in-repo `gateway/worker.js`, and deploy it as `s27-portal-gateway` (the URL `dashboard.js` already points at, line 60).**

Justification:
- **Keeps the frontend contract untouched.** `GATEWAY_BASE` does not change, so there is no frontend rewrite and the `{ok,status,data}` parse + 401/403 handling keep working.
- **Auditable & version-controlled.** The code lives in this repo (the only repo in scope), unlike `s27-portal-gateway-v2` whose source is not in the repo.
- **Reuses existing trust plumbing.** `verifyFirebaseToken`, the claim→`bedrijf_id` derivation, `GATEWAY_SECRET`, and origin checks already exist in `gateway/worker.js`.
- **Incremental + reversible.** Add `const D1_ENABLED = new Set(JSON.parse(env.D1_ENDPOINTS||'[]')); if (D1_ENABLED.has(path)) return d1Handler(path, bedrijfId, body, env);` before the Make forward. Default empty ⇒ zero behaviour change on deploy; flip endpoints one at a time via the env var; instant rollback by removing one.

Rejected alternatives:
- **Option B (point frontend at `gateway-v2`):** its source is not in the repo (out-of-scope/unversioned), and its portal handlers still hit ClickUp, not D1 — so it is net-new work either way. Reject for an auditable migration.
- **Option C (frontend calls the hub D1 directly):** forces a frontend rewrite and re-implements auth/CORS/scope on the client — highest blast radius. Reject.

**Required env/binding wiring (confirm with user):** add D1 binding `CRMDB → 0c50db87-9a69-4cdc-9f43-4c1dc92dd801`, the `D1_ENDPOINTS` feature-flag var, and confirm the Firebase claim carries `is_staff` if any staff act-as is needed from the portal worker. Keep external-effect endpoints (Drive/Calendar/PandaDoc/Metricool/Meta) as direct-API handlers ported into the repo worker, never faked from D1.

**This recommendation needs user confirmation** (which gateway the team wants to keep evolving; see §11).
